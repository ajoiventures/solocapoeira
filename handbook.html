Build products like
a head of studio.

This handbook is built from real work — every project session adds a lesson. The goal: run the entire product development process — from idea to live product — using AI as your execution layer, with you as the director.

How to use this

Read linearly once. Then use it as a reference before starting any new project or feature. Each chapter ends with a Before You Leave checklist. Do those before writing code.

Chapter 01

The Core Loop

Every successful product has one action users repeat. Get this wrong and no feature will save you.

What a core loop is

A core loop is the single repeating action that drives all value in your product. It's what users do every time they open the app. Everything else — progression, social, monetization — wraps around it.

Trigger
User opens app
motivation
Action
Core activity
the loop
Reward
Visible progress
dopamine
Investment
Raises stakes
retention
Trigger
Stronger urge
next session

Solo Leveling core loop: Log reps → mastery advances → new movement unlocks → train it → log reps. Every feature either feeds this or it's a distraction.

Define it before writing a line of code

The single most expensive mistake in product development is building features before the core loop is proven. EA studios spend 3–6 months on a prototype of just the core loop before greenlighting full production.

1
Write the loop in one sentence
If you can't explain the loop in one sentence, you don't understand it yet. "Users do X, then Y happens, which makes them want to do X again."
2
Keep the action short
The action must be completable in <3 minutes. If it takes longer, most users won't finish it, which means the reward never lands.
3
The reward must be visible and immediate
Progress bars, XP ticks, level-ups, sound effects. Invisible rewards don't work. Users need to see the number go up.
4
Investment locks users in
Streak count, mastery level, unlocked content — these are "sunk costs" that make leaving feel expensive. Build them early.

Secondary and tertiary loops

Once the core loop works, you layer longer loops around it:

Loop typeTimeframeExamplePurpose
Core2–5 minLog reps → advanceDaily habit
Session15–30 minComplete quest → bonus XPSession length
Weekly7 daysStreak → grace tokenD7 retention
Monthly30 daysMonthly challengeD30 retention
PrestigeMonthsDefeat all Mestres → EhiEndgame retention
EA lesson — why games fail

The #1 reason good games fail: the core loop works but there's no secondary loop to pull you back tomorrow. Players finish a session satisfied — and never return. Session satisfaction ≠ retention.

Before you leave ✓

  • Write the core loop in one sentence
  • Can a new user complete one full loop in <5 minutes?
  • Is the reward for completing it visible and instant?
  • Is there a reason to come back tomorrow (investment)?
  • Have you identified your D1/D7/D30 loop layers?
Chapter 02

AI Workflow

How to use Claude and OpenAI as a senior co-founder — not a code monkey. The difference is in how you brief it.

The mental model

You are the director. AI is the studio. Directors don't write every line — they define what must be true and let the studio execute. Your job is to have taste, make decisions, and review outputs. AI's job is to generate options, implement specs, catch issues you missed.

The key insight

AI gives you the execution capacity of a 10-person team. The bottleneck is no longer "who will build this" — it's "what should be built, in what order, to what spec." Your leverage is entirely in the quality of your decisions and briefs.

Model selection

ModelBest forCostWhen to use
Claude SonnetCode, long files, data workMediumDefault for all implementation
Claude OpusArchitecture, hard decisions, strategyHighDesign sessions, reviewing plans
Claude HaikuRepetitive tasks, transformsLowBulk data generation, formatting
GPT-4oSecond opinion, different angleMediumWhen Claude is stuck or wrong
o3/o1Hard reasoning, math, algorithmsHighComplex logic, data structures

Token efficiency rules

Tokens = time + money. These rules cut waste by 60% without losing quality:

1
Front-load context, not history
Don't re-explain what was done. Explain what is true NOW — current file state, current constraint, current goal. Claude reads code better than it reads summaries of code.
2
One ticket per prompt
Batching 5 features into one prompt produces 5 half-finished features. One clear ticket → one complete implementation you can actually review.
3
Define done before you start
"Add a chart" is not a spec. "Add a 30-bar SVG chart on the Body page showing daily VIG, colored green/amber/red by quality, pulling from recoveryLog" is a spec. Vague briefs produce vague output.
4
Use subagents for parallel work
When two features don't depend on each other, run them in parallel (Agent tool). Cut wall-clock time 40–60% on large batches.
5
Never paste full files. Point to lines.
Instead of pasting 300 lines, say "in DailyQuest.jsx:1420, the FlowSession timer…" Claude will read it. Pasting wastes context for everyone.
6
Test immediately after every feature
Run npm test after each ticket, not after a batch. Catching failures early = fewer tokens fixing cascading issues later.
7
Use memory files
Save key decisions, constraints, and user preferences to memory. Claude re-reads these at the start of each session — you don't re-explain them. The MEMORY.md file IS your product brain.

The perfect prompt structure

TICKET: [ID] — [Title]

CONTEXT:
What is true right now. Current state. What was tried. What exists.

GOAL:
Exactly what done looks like. Be specific. Include file paths and line numbers if relevant.

CONSTRAINTS:
Things it must not break. Edge cases. Performance requirements.

SPEC:
1. Step-by-step what needs to happen
2. Data shape if relevant
3. Where in the codebase it lives

DONE WHEN:
- Concrete checkable criteria
- Tests pass
- No console errors
- Specific UI behaviour works

When to use Claude vs OpenAI

Use Claude as your default. Switch to GPT-4o when:

  • Claude keeps making the same mistake after 2 corrections — try OpenAI for a fresh angle
  • You want a genuine second opinion on architecture (not a rubber stamp)
  • File is >4000 lines — GPT-4o's context window can sometimes handle differently
  • You're doing complex function calling / structured JSON output at scale

Use o3 when the problem requires deep reasoning: algorithm design, security analysis, complex data structure decisions.

Session discipline

Each working session should have:

  1. One goal. "Today I'm shipping X." Not "I'll see what I can do."
  2. A ticket list. Pull from the backlog. Commit to 2–4 tickets max.
  3. A build check at the end. npm run build clean before closing.
  4. A memory update. Did anything surprise you? Save it.
Token budget per session
Small session
~50K
1–2 focused tickets, no research
Normal session
~200K
4–6 tickets, some exploration
Architecture session
~500K
Refactors, system design, testing

If you're burning more than 500K on a session without shipping tangible features, you're exploring instead of executing. Write a spec, restart.

Before you leave ✓

  • Did every prompt have a clear DONE WHEN criteria?
  • Did you run tests after each ticket?
  • Is there anything surprising from this session to save to memory?
  • Did you update the ticket board (done / in progress)?
  • Clean build before closing?
Chapter 03

Project Anatomy

Every project needs the same skeleton. Build it once, reference it forever.

The five files every project needs

1
tickets.html — the board
Every feature is a ticket. Tickets have IDs, priorities, statuses. You should know at a glance what's blocked, what's ready, what's done. Rebuild this on every project.
2
handbook.html — this file
The living playbook. Grows every session. Reference it before starting new work. Don't rebuild from scratch — carry it forward.
3
MEMORY.md — the brain
Key decisions, user preferences, constraints. Loaded at the start of every AI session. Without it, you repeat yourself every session. With it, you build on prior work.
4
data-integrity tests — the guard
Cross-reference tests that catch data bugs before they reach users. Run on every commit. In Solo Leveling they caught 15 real bugs that were silently wrong.
5
CLAUDE.md — the briefing doc
Project context for AI: tech stack, conventions, what's off-limits, key file paths. Claude reads this at session start. 20 minutes writing this = hours saved per week.

Phase structure

Every project runs through the same four phases. The mistake is skipping phases or running them out of order.

PhaseGoalWhat you buildExit criteria
A — BaselineFoundation that should have existed day 1Tests, CI/CD, auth, error monitoring, file structureClean build, 80%+ test coverage on core logic, no silent failures
B — Score improvementsMove each department from failing to passingOnboarding, empty states, key features, analyticsD1 retention > 40%, no critical UX failures
C — Score maximizersMove each department from good to greatPerformance, accessibility, deep gamification, full test suiteLCP <2s, WCAG AA, D7 retention >25%
D — ExpansionGo deeper, not widerContent depth, community, live ops, monetizationD30 retention >15%, NPS >40

Folder structure (React + Vite)

src/
  data/          ← All static data (no logic, pure exports)
  store/         ← State management (split by domain: usePlayerStore, etc.)
  pages/         ← One file per screen. Keep under 400 lines.
  components/    ← Shared UI. Dumb components, no store imports.
  utils/         ← Pure functions. Fully testable.
  __tests__/     ← Colocated with what they test
scripts/         ← One-shot migration/generation scripts
CLAUDE.md        ← AI briefing doc
tickets.html     ← Project board
handbook.html    ← This file
The 400-line rule

Any file over 400 lines is doing too many things. Split it. In Solo Leveling, useStore.js grew to 1400 lines and DailyQuest.jsx to 1900 — both are now technical debt. Split early, not after.

State schema rules

  1. Version your state. Add _v: 1 to every localStorage save. When you change the schema, write a migration function.
  2. Never lose user data. Always deep-merge saved state with default state — new keys get default values, existing keys are preserved.
  3. Test save/load on Day 1. The most common failure: app works but importing old data breaks silently.
  4. Separate UI state from persistence. achievementQueue (toast queue) should never persist to localStorage. earnedAchievements should.

Before you leave ✓

  • Do all five core files exist?
  • Is every page under 400 lines?
  • Is the state versioned and migration-ready?
  • Are tests running and covering core logic?
Chapter 04

Week One Playbook

The first week determines everything. What you skip here becomes technical debt that compounds forever.

Day 1 — Foundation only

Do not write a single feature. Do not touch UI. Do this:

  • Define the core loop in one sentence. Write it on a sticky note.
  • Set up the repo — Vite + React (or your stack). Clean slate.
  • Write CLAUDE.md — tech stack, conventions, what not to touch.
  • Create tickets.html — with Phase A tickets only. Fill Phase B–D later.
  • Define the state schema — what data does the app need? Write it as a JS object with comments before you write any code.
  • Set up error monitoring — Sentry free tier, 30 minutes. You will regret skipping this.

Day 2 — Core loop prototype

  • Build the bare minimum version of the core loop. No styling, no polish.
  • Can a user complete one loop from start to finish?
  • Is the reward visible and immediate?
  • Show it to one person outside the project. Watch them use it. Don't explain anything.

Day 3–4 — Make it feel real

  • Add the data layer — real content, not placeholders.
  • Add persistence — localStorage at minimum.
  • Write your first tests — core math and state logic only.
  • Add analytics — PostHog or equivalent. Instrument the core loop action.

Day 5–7 — First user feedback

  • Deploy to a real URL (Vercel/Netlify free tier, 10 minutes).
  • Send to 3–5 real users in your target audience. Not friends. People who actually do the thing your app is about.
  • Watch the analytics. Where do they drop off?
  • Fix the #1 drop-off point before building new features.
EA's biggest lesson on week one

EA's most successful studios run a "First Playable" review in Week 1. A rough, ugly prototype that proves the core loop is fun. If you can't prove the loop is engaging in week 1, you are building on sand. Stop. Rethink the loop.

What to skip in Week One

  • User accounts / auth (use localStorage)
  • Payment / monetization
  • Multiple platforms
  • Settings / preferences
  • Nice-to-have features
  • Pixel-perfect design

Before you leave ✓

  • Is the core loop completable end-to-end?
  • Has one real user seen it?
  • Is it deployed to a real URL?
  • Is analytics installed and tracking the core action?
  • Do you have a ticket board with Phase A complete and Phase B–D stubbed?
Chapter 05

Retention Mechanics

Getting users on Day 1 is marketing. Getting them back on Day 7 is product. This is where the real game is played.

The retention curve

Every product has a retention curve — % of users still active N days after signup. Industry benchmarks for consumer apps:

DayPoorAverageGoodBest-in-class
D1<20%25–35%40–50%>60%
D7<5%10–15%20–30%>40%
D30<2%5–8%10–20%>25%

Training/fitness apps (like Solo Leveling) target higher because they replace a real habit. Aim: D1 >50%, D7 >30%, D30 >20%.

The mechanics that work

1
Streaks
The most powerful retention mechanic ever built. The fear of losing a streak pulls users back on days they'd otherwise skip. Add grace tokens to make streaks feel fair, not punishing. Duolingo's entire retention strategy is built on this.
2
Daily quests with variable rewards
Fixed quests get ignored. Variable rewards (daily bonus challenge rotating 30 ways) trigger the dopamine system. The key: every day must feel slightly different from the last.
3
Near-miss progression
The most powerful moment is when a user is "just 12 reps from Owning." Show the gap clearly. This is why progress bars with visible endpoints outperform abstract XP.
4
Weekly + monthly goals
Streaks are daily. Weekly reports and monthly challenges create mid-term goals that survive missed days. A user who breaks their streak still has a monthly challenge to care about.
5
Push notifications at the right time
At 7pm local time if they haven't trained yet. Not earlier (annoying), not later (too late). The message: "Your streak is at risk." Tested: 35% open rate vs 8% average.
6
Endgame content
Users with no long-term goal to work toward stop logging in after D30. Mestres → Orishas → Ehi ascension is an endgame. Every product needs one. "What's left to achieve" must always have an answer.
The retention test

Ask yourself: why would a user open this app on a Sunday evening when they're tired? If you can't answer that, you don't have D7 retention. The streak fear, the near-miss, the daily challenge expiring — these are the answers.

Before you leave ✓

  • Is there a daily reason to return (quest, streak, challenge)?
  • Is the user's streak investment visible and meaningful?
  • Is there a "near miss" moment visible to the user right now?
  • Is there endgame content for your most engaged users?
  • Are you tracking D1/D7/D30 retention in analytics?
Chapter 06

Shipping Discipline

A feature that's 95% done and not shipped is worth 0. A feature that's 80% done and shipped is worth everything.

The shipping test

Before marking any ticket done, run this checklist:

✓
Build passes
npm run build exits 0. No console errors in production build.
✓
Tests pass
npm test all green. Any new logic has at least one test.
ok
Page states are locked
For critical screens, snapshot the user-visible states, not just data shapes. DailyQuest now locks Day 1, mid-sprint, rest day, and all-done states.
✓
Golden path works
Open the app as a new user. Complete the feature. Does it work as intended?
✓
Edge cases handled
Empty state (no data), first-time user, max data (10,000 reps). None should crash.
✓
Mobile works
DevTools mobile viewport. Tap targets ≥44px. Nothing overflows.

What NOT to gold-plate

Perfection is the enemy of shipping. These things do not need to be perfect to ship:

  • Copy — placeholder text ships. Polish copy in v2.
  • Animations — functional first. Delightful later.
  • Edge cases that affect <1% of users — file a ticket, move on.
  • Design consistency — close enough ships. Pixel-perfect in a design pass.

The batch discipline

Work in batches of 3–5 related tickets. After each batch:

  1. Clean build
  2. All tests green
  3. Update ticket board
  4. One-line daily log entry
  5. Deploy if possible
Ship daily

The best studios ship something to production every single day. Not a full feature — even a copy change, a bug fix, a performance tweak. Daily shipping = daily feedback = faster learning. If you go 3 days without shipping, you're over-engineering something.

Before you leave ✓

  • Did you ship something today? (Even one small thing?)
  • Are all completed tickets marked done on the board?
  • Is the build clean?
  • Are critical page states covered by a focused snapshot or E2E check?
  • Is there a daily log entry for today?
